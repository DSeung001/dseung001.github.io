1. Backend 핵심 역량
6년 8개월 동안 서버 개발, 데이터 처리, 성능 개선과 서비스 운영을 경험했습니다.
Go를 중심으로 의료기기 연동과 데이터 처리 시스템을 개발했고, 이벤트 서비스와 데이터 수집 시스템을 거치면서 AWS 환경의 배포, 운영, 장애 대응도 경험했습니다.
특정 기술을 사용하는 것보다는 서비스가 전체적으로 어떻게 동작하는지 먼저 보고, 문제가 생기면 원인을 찾아 현재 환경에 맞는 방식으로 개선하면서 개발해왔습니다. 
최근에는 이 경험을 미디어 도메인으로 넓히기 위해 영상 업로드, 비동기 인코딩, HLS 변환, Storage/CDN 전달, 검색과 RAG까지 직접 구현하고 운영하고 있습니다.

2. 실제 서비스에서의 Backend 경험
휴비츠에서는 병원 사설 네트워크에서 운영되는 온프레미스 서비스의 백엔드와 의료기기 데이터 처리 구조를 담당했습니다.
신규 의료기기 연동 과정에서 통신 방식과 데이터 저장 흐름을 정리했고, Go 동시성을 이용한 병렬 처리로 이미지 처리 시간을 11초에서 4초로 줄였습니다. 
의료장비와 웹 서버의 통신 중 반복적인 DB 접근이 발생하는 부분에는 로컬 캐싱을 적용해 DB Connection 사용률을 100%에서 78%로 낮췄습니다. 
레거시 코드에서는 한 번에 크게 바꾸기보다는 책임을 조금씩 나누면서 로깅, 에러 처리와 단위 테스트를 개선했습니다.

의료,안광학처럼 도메인 지식이 필요한 부분은 관련 전문가에게 확인하면서 진행했고, 이를 실제 시스템으로 구현하는 과정에서는 데이터 구조, 인터페이스와 안정성 등 개발자가 담당해야 하는 부분을 책임졌습니다. 
소규모 팀에서 프로젝트 전체 진행 상황에 맞춰 업무를 조율했고, 장애나 요구사항 변경이 생기면 제 코드만 보기보다 앞뒤 데이터 흐름을 같이 확인하면서 원인을 찾았습니다.

비트리에서는 짧은 기간에 사용자가 몰리는 DAU 10만 규모 이벤트 서비스를 개발하고 운영했습니다. 
추첨과 상품 지급 과정에서 동시에 요청이 들어왔을 때 상품이 중복 지급되는 문제를 막기 위해 Redis Queue 기반 처리 구조를 적용했습니다.
AWS EC2, S3, CloudWatch, CloudFront 환경에서 개발, 배포, 모니터링과 장애 대응까지 경험했습니다.

데이터 수집 업무에서는 Amazon 상품 약 100만 건을 약 17K회의 요청과 약 50달러의 비용으로 수집하면서, 요청 수와 비용을 같이 고려한 데이터 수집 구조를 구현했습니다.

3. TVING API Platform과 연결되는 미디어 처리 경험
개인 프로젝트 Class S를 실제로 배포해 사용하면서 영상 업로드부터 재생까지 이어지는 미디어 Backend 구조를 직접 만들고 개선했습니다.
Client → Presigned URL → S3 → PublishJob → SQS → Encoding Worker → FFmpeg HLS → S3/CloudFront → Client
처음에는 대용량 영상이 Backend API를 거쳐 S3에 저장되는 구조였습니다. 
영상 크기가 커질수록 API 서버의 메모리와 디스크를 점유할 수 있다고 판단해 Presigned URL 기반 Direct Upload 방식으로 변경했습니다. 
이후 API 서버는 권한 확인, 메타데이터 검증, 상태 관리와 Job 생성에 집중하도록 역할을 나눴습니다.

인코딩도 처음에는 Celery/Redis 기반 단일 서버에서 처리했지만, API 서버와 인코딩 작업의 리소스 사용 패턴이 다르다고 판단해 SQS와 Auto Scaling 기반의 별도 Worker 구조로 변경했습니다. 
API와 인코딩을 각각 확장할 수 있도록 구성했고, 인프라 구조를 조정하면서 일 운영 비용도 약 3달러에서 1.17달러 수준으로 줄였습니다.

운영 중에는 완료된 비동기 Job이 다시 전달돼 재실행되는 문제가 있었고, 원인을 확인한 뒤 중복 실행을 막는 로직을 추가했습니다. 
특정 WebM/VFR 영상에서는 비정상적인 FPS 메타데이터 때문에 인코딩이 4시간 이상 걸리는 문제가 있었는데, 프레임 타임라인을 확인해 원인을 찾고 약 40분 수준으로 줄였습니다. 
배포 과정도 GitHub Actions와 ECR을 이용해 자동화했습니다.

TVING의 서비스 규모와는 차이가 있지만, VOD 서비스에서 필요한 콘텐츠 상태 관리, 비동기 Job, 미디어 처리, Storage/CDN 전달, 장애와 재처리 문제를 직접 구현하고 경험했습니다. 
이런 경험을 TVING API Platform의 미디어 데이터 처리와 API 개발에 이어가고 싶습니다.

4. 검색,AI 기능을 서비스에 연결한 경험
Class S에서는 PostgreSQL FTS와 Embedding을 결합한 Hybrid Search를 구현했고, 콘텐츠를 청크 단위로 나눠 검색과 RAG에서 같은 데이터를 사용할 수 있도록 구성했습니다.
검색 랭킹 역시 정해진 값을 그대로 사용하는 것보다 실제 결과를 확인할 필요가 있다고 생각해 사용자 행동 데이터를 수집하고, 서로 다른 검색 랭킹을 비교할 수 있는 A/B Test 구조를 구현했습니다.

RAG 기능은 단순히 LLM API를 호출하는 방식으로 끝내지 않고,
Hybrid Search → Context 구성 → LLM 응답 → Schema 검증 → 잘못된 결과 필터링 → Fallback → Golden Dataset 평가
순서로 구성해 결과의 품질을 검증할 수 있도록 했습니다.

AI 기능도 결국 서비스 안에서 동작하는 기능이라고 생각했습니다. 
결과를 만드는 것뿐 아니라 기존 데이터와 어떻게 연결할지, 잘못된 결과는 어떻게 막을지, 결과가 제대로 나오는지는 어떻게 확인할지까지 같이 고려하면서 구현했습니다.

5. TVING에서 활용할 수 있는 경험
TVING API Platform에서 미디어 데이터와 상태를 안정적으로 제공하는 API, 비동기 처리, 장애 복구와 성능 개선 업무에 지금까지의 경험을 활용하고 싶습니다.
SI/SM, 이벤트 서비스, 데이터 수집, 온프레미스 시스템과 미디어 프로젝트까지 서로 다른 환경에서 개발하면서 하나의 기술이나 방식이 항상 정답은 아니라는 것을 배웠습니다. 
현재 시스템의 구조와 문제가 무엇인지 먼저 확인하고, 그 환경에서 필요한 방법을 선택하면서 개발해왔습니다.
TVING에서도 문제가 생겼을 때 한 부분만 보기보다 요청부터 데이터 저장, 비동기 처리와 클라이언트 전달까지 전체 흐름을 확인하면서 원인을 찾고 개선하는 Backend Engineer로 기여하고 싶습니다.
