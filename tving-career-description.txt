TVING 경력기술서

지원 동기와 강점 요약

저는 총 6년 8개월 동안 서버 개발, 데이터 처리, 저장 구조 개선, 서비스 운영을 경험한 백엔드 개발자입니다. Go 기반 의료기기 연동, Java/Spring 및 Laravel 이벤트 서비스, Python 데이터 수집을 거쳤고, 최근에는 개인 프로젝트 Class S에서 동영상 업로드, 비동기 인코딩, HLS 변환, S3/CloudFront 배포, 검색/RAG 기능까지 직접 설계하고 운영하고 있습니다.

TVING의 API Platform과 Service Platform 직무는 여러 클라이언트가 사용하는 API, 미디어 도메인의 데이터 흐름, 대용량 트래픽과 비동기 처리, 실험과 로그 기반 개선 환경을 함께 다루는 역할이라고 이해했습니다. 저는 대규모 OTT 운영 경험이 있는 것은 아니지만, 실제 사용자가 있는 서비스에서 업로드, 시청, 검색, 알림, AI 분석, 인코딩, 장애 대응을 하나의 흐름으로 연결하며 운영 가능한 구조를 만들어 왔습니다.

Class S 미디어/API 플랫폼 프로젝트

Class S는 강의 녹화본을 업로드하고 HLS로 변환해 시청할 수 있는 개인 프로젝트입니다. API가 메타데이터와 상태를 관리하고, 워커가 비동기로 인코딩한 뒤 결과물을 S3와 CloudFront로 제공하는 미디어 파이프라인으로 설계했습니다. 이 구조는 VOD 콘텐츠의 업로드, 발행, 전시, 재생 데이터를 클라이언트에 안정적으로 제공해야 하는 TVING API Platform의 문제와 맞닿아 있다고 생각합니다.

초기에는 브라우저가 백엔드 API로 multipart 파일을 보내고, 백엔드가 S3에 업로드한 뒤 Celery/Redis 워커가 FFmpeg HLS 인코딩을 수행했습니다. 운영 중 대용량 영상이 API 서버의 메모리와 디스크를 압박할 수 있음을 확인했고, Presigned URL 기반 Direct S3 업로드로 전환했습니다. 현재는 init API에서 Job과 presigned PUT URL을 발급하고, 클라이언트가 S3에 직접 업로드한 뒤 commit API로 검증과 큐잉을 진행합니다. API 서버는 권한 확인, 메타데이터 검증, 상태 전이, 큐 등록에 집중하도록 책임을 분리했습니다.

비동기 처리도 단계적으로 개선했습니다. PublishJob은 uploading, queued, processing, completed, failed 상태를 갖고, 프론트는 Job 상태를 조회해 진행률을 확인합니다. 이후 비용과 확장성을 위해 Celery/Redis 단일 서버 구조에서 SQS, CloudWatch, ASG 기반 인코딩 워커 분리 구조로 발전시켰습니다. API 서버는 저사양 EC2에서 요청을 처리하고, SQS 메시지가 쌓이면 ASG가 인코딩 EC2를 늘리며, 워커가 S3 저장과 DB 상태 갱신, 메시지 ack를 수행합니다. 이 변경으로 일 비용을 약 3달러에서 1.17달러 수준까지 낮췄습니다.

운영 장애도 직접 분석했습니다. Celery/Redis 환경에서는 visibility_timeout과 worker_prefetch_multiplier 설정으로 완료된 작업이 재전달되어 삭제된 S3 staging 파일을 다시 읽는 NoSuchKey 문제가 발생했습니다. 이를 설정 조정과 완료 Job 재실행 방지 로직으로 보완했습니다. 특정 WebM/VFR 영상에서 왜곡된 1000fps 메타데이터로 인코딩이 4시간 이상 지연되는 문제도 프레임 타임라인 분석 후 CFR 30fps 출력으로 고정해 약 40분 내 처리되도록 개선했습니다.

AI/RAG 및 검색 실험 플랫폼 경험

Class S에서는 업로드된 강의 콘텐츠를 더 잘 찾고 활용하기 위해 검색과 AI 기능을 확장했습니다. OpenAI Whisper 또는 YouTube 자막으로 transcript를 만들고, Gemini로 설명, 태그, 타임라인을 생성한 뒤 사람이 검수하고 발행하는 흐름을 구성했습니다. 최종 발행 이후에는 search_index 잡이 강의명, 영상명, 설명, 태그, 타임라인, 자막 구간을 청크로 만들고 PostgreSQL FTS와 1536차원 임베딩 벡터를 함께 저장합니다.

검색 API는 키워드 점수, 의미 유사도, 조회수를 결합한 하이브리드 랭킹 방식으로 구성했습니다. OpenAI 키와 임베딩 모델 버전이 맞으면 vector 검색을 포함하고, 없으면 FTS 기반으로 동작하게 했습니다. 이후 SearchExperiment, SearchExperimentConfig, SearchBehaviorEvent 테이블을 두고 검색 랭킹 가중치 A/B 테스트 구조를 만들었습니다. 검색 결과 노출 후 10초 안에 play 또는 seek가 발생하면 성공으로 보고 success@10s, uplift, p-value, verdict를 Admin에서 비교할 수 있게 했습니다.

RAG 기반 강의 추천 챗봇도 구현했습니다. POST /api/v1/rag/chat API에서 질문을 받고, 하이브리드 검색으로 찾은 SearchChunk를 Course/Video/Evidence context로 구성한 뒤 Gemini가 JSON schema에 맞춰 추천 강의와 관련 구간을 반환하게 했습니다. Context에 없는 id는 후처리로 걸러냈고, 검색 결과가 부족하면 no_result로 응답하게 했습니다. Golden Dataset 평가 구조도 구성해 소량 검증 기준 13건 전체 pass, course/video hit 1.0, 평균 generation 약 1.74초를 확인했습니다.

이전 경력: Go, MySQL, Redis, AWS 운영 경험

휴비츠에서는 병원 사설 네트워크에서 운영되는 온프레미스 웹 서비스의 백엔드 개발과 데이터 처리 구조 개선을 담당했습니다. 신규 의료기기 연동을 위해 통신 방식과 데이터 저장 흐름을 정의했고, Go 기반 이미지 처리 로직에 병렬 처리를 도입해 처리 시간을 11초에서 4초로 줄였습니다. 또한 의료 데이터 로컬 캐싱을 적용해 장비 통신 시 DB 커넥션 사용률을 100%에서 78%로 낮췄고, MySQL 기반 데이터 구조를 다루며 로깅, 에러 처리, 단위 테스트를 점진적으로 개선했습니다.

비트리에서는 이벤트성 웹 서비스와 기업 웹사이트의 개발, 배포, 운영, 유지보수를 담당했습니다. 추첨, 포인트, 코드 입력 등 트래픽이 몰리는 이벤트 기능을 개발했고, DAU 10만 규모 이벤트 운영과 실시간 이슈 대응을 경험했습니다. Redis Queue로 상품 중복 당첨을 방지했으며, AWS EC2, S3, CloudWatch, CloudFront 환경에서 배포와 모니터링, CS 대응까지 맡았습니다. 에이아이썸에서는 Amazon 상품 데이터 약 100만 건을 약 17K requests, 약 50달러 비용으로 수집하며 HTTP 요청 최적화와 스케줄링 경험을 쌓았습니다.

TVING에서 기여하고 싶은 방향

TVING에 합류한다면 미디어 도메인 API와 비동기 처리, 운영 가능한 공통 플랫폼 개발에 빠르게 기여하고 싶습니다. 웹, 모바일, TV 클라이언트가 각기 다른 요구사항을 갖는 환경에서 API는 콘텐츠 상태, 권한, 실험, 캐시, 로그, 장애 대응을 함께 고려해야 하는 제품의 기반이라고 생각합니다. Class S에서는 Redis Pub/Sub와 SSE 기반 알림도 구현했고, AI 협업 도구를 문제 분석과 구현 속도 향상에 적극 활용해 왔습니다.

앞으로는 TVING의 Service Platform과 API Platform에서 여러 개발 조직이 안정적으로 사용할 수 있는 API와 백오피스, 실험/로그 기반 플랫폼을 만드는 데 기여하고 싶습니다. 새로운 기술을 도입하는 것보다 현재 서비스의 병목과 실패 지점을 먼저 관찰하고, 필요한 만큼 단순하고 검증 가능한 구조로 바꾸는 개발자가 되고 싶습니다.
